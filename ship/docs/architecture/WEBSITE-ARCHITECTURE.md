# Phase 0 Architecture — System Architecture Document

## System Overview
The Ji Sushi Prepnest website platform (`/ship`) is designed for maximum reliability and continuous operation under all network and database conditions.

```
                         [ Customer Browser / Mobile ]
                                       |
                                       v
                             [ Next.js API Routes ]
                                       |
                   +-------------------+-------------------+
                   | (Normal Path)                         | (Failover Path)
                   v                                       v
          [ Supabase PostgreSQL ]                  [ Trusted Fallback Menu ]
                   |                                       |
                   +-------------------+-------------------+
                                       |
                                       v
                            [ Google Sheets Mirror ]
                                       |
                            [ Google Apps Script ]
```

---

## 1. Datastores & Storage Strategy

### Primary Datastore: Supabase (PostgreSQL)
- Stores canonical `orders`, `menu_items`, `system_events`, `outbound_messages`, `loyalty_customers`, and `settings`.
- Enforces strict schema constraints, status validations (`pending`, `accepted`, `ready`, `completed`, `cancelled`), and unique indexes on `idempotency_key` and `public_token`.

### Independent Secondary Datastore: Google Sheets
- Acts as a real-time mirror during normal operation and independent primary intake store during Supabase outages.
- Communicates via Google Apps Script webhooks.

### Local Trusted Static Fallback Catalog: `data/menu-fallback.json`
- Contains all 101 menu items with prices, categories, and allergen data.
- Read server-side during checkout if Supabase PostgreSQL or API connectivity is unavailable.

---

## 2. Checkout Flow Architecture

### Normal Mode (Supabase Healthy)
1. Client submits cart payload with an `idempotency_key` (UUID v4) generated per attempt.
2. Server validates rate limit, items limit, phone format, and opening hours.
3. Check Supabase for replay (`idempotency_key` match). Return existing order if found.
4. Read current prices and availability from Supabase `menu_items`.
5. Price order server-side (`priceOrder`). Client prices are ignored.
6. Insert order into Supabase `orders` table. Generate sequential `order_no` and unguessable `public_token`.
7. Asynchronously mirror order to Google Sheet via webhook.
8. Enqueue notification / SMS via `outbound_messages`.
9. Return `{ ok: true, orderNo, token, total }`.

### Degraded Mode (Supabase Unreachable)
1. If Supabase fails during menu lookup or insert:
2. Load prices and availability from trusted server-side `data/menu-fallback.json`.
3. Validate and price order server-side using fallback menu.
4. Generate emergency order ID (`N` + timestamp digits).
5. Post order directly to Google Sheets webhook (`mirrorToSheet`).
6. If Google Sheet accepts the order, return `{ ok: true, degraded: true, orderNo, status: 'pending' }`.
7. If both Supabase and Google Sheet fail, return `{ ok: false, error: '...' }` with instructions to call the restaurant directly.

---

## 3. Reconciliation Architecture
- When Supabase is restored, a deterministic reconciliation process executes (Phase 5).
- Reads emergency orders from Google Sheet (identified by source and `idempotency_key`).
- Checks Supabase for existing order with matching `idempotency_key`.
- Inserts missing orders into Supabase, tagging them with `reconciled: true`.
- Idempotent execution guarantees running reconciliation $N$ times produces the same result as running it once.

## 4. API & Database Contracts (Staff App Preserved)

### Orders Table Schema (`orders`)
```sql
CREATE TABLE orders (
  id UUID DEFAULT gen_random_uuid() PRIMARY KEY,
  order_no INT GENERATED BY DEFAULT AS IDENTITY,
  customer_name TEXT,
  customer_phone TEXT,
  table_number INT,
  items JSONB NOT NULL,
  status TEXT DEFAULT 'pending' CHECK (status IN ('pending','accepted','ready','completed','cancelled')),
  total_price NUMERIC(10,2),
  created_at TIMESTAMPTZ DEFAULT NOW(),
  pickup_minutes INT,
  completed_at TIMESTAMPTZ,
  idempotency_key TEXT UNIQUE,
  public_token TEXT UNIQUE,
  accepted_at TIMESTAMPTZ,
  ready_at TIMESTAMPTZ,
  cancelled_at TIMESTAMPTZ,
  cancel_reason TEXT,
  ready_estimate TIMESTAMPTZ,
  channel TEXT DEFAULT 'takeaway',
  phone_digits TEXT GENERATED ALWAYS AS (regexp_replace(COALESCE(customer_phone, ''), '[^0-9]', '', 'g')) STORED
);
```

### Table Booking Contract Proposal (Phase 6)
```sql
CREATE TABLE IF NOT EXISTS reservations (
  id UUID DEFAULT gen_random_uuid() PRIMARY KEY,
  reservation_no INT GENERATED BY DEFAULT AS IDENTITY,
  customer_name TEXT NOT NULL,
  customer_phone TEXT NOT NULL,
  customer_email TEXT,
  reservation_date DATE NOT NULL,
  reservation_time TIME NOT NULL,
  guests INT NOT NULL,
  message TEXT,
  status TEXT DEFAULT 'pending' CHECK (status IN ('pending','confirmed','rejected','cancelled')),
  created_at TIMESTAMPTZ DEFAULT NOW()
);
```
